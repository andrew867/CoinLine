# ShadyBank merchant authorization

CoinLine can use the scoped ShadyBank merchant instrument API to reserve funds for a recognized synthetic magnetic-card request and a recent matching native quote. It is an independent opt-in alternative to the existing synthetic ledger provider. Both are disabled by default; select only one provider per host instance to avoid ambiguous settlement policy.

Configure the bank's separate merchant service and an authorized opaque instrument token first. The provider sends only the token, quoted amount and a deterministic request UUID; it never sends the terminal's PAN, raw track, PIN, NCC frame or dialed number. The service key and instrument token belong in environment variables or user-secrets, never in committed settings. HTTPS is required except for an explicitly enabled loopback-only lab connection. Redirects and cookies are disabled.

| Configuration key | Meaning |
| --- | --- |
| `CardPayments__ShadyBankAuthorization__Enabled` | Explicit opt-in |
| `CardPayments__ShadyBankAuthorization__ServiceUrl` | Exact merchant authorization endpoint ending in `/api/merchant/authorize` |
| `CardPayments__ShadyBankAuthorization__ServiceKey` | Private scoped merchant key |
| `CardPayments__ShadyBankAuthorization__AllowLoopbackHttp` | Allow HTTP only at a loopback endpoint in a local lab |
| `CardPayments__ShadyBankAuthorization__Bindings__0__TerminalId` | Explicit registered synthetic terminal UUID |
| `CardPayments__ShadyBankAuthorization__Bindings__0__Destination` | Exact reserved synthetic test route |
| `CardPayments__ShadyBankAuthorization__Bindings__0__InstrumentToken` | Bank-issued private opaque instrument token |
| `CardPayments__ShadyBankAuthorization__Bindings__0__AllowAuthorizationOnlyRate` | Disabled by default. For a qualified legacy synthetic MT2 route that sends authorization before a separate terminal quote, allow an initial one-minute charge from the effective published host plan |
| `CardPayments__ShadyBankAuthorization__CaptureUploadedCalls` | Disabled by default. Enable the separately qualified merchant capture workflow |
| `CardPayments__ShadyBankAuthorization__Bindings__0__AllowCaptureUploadedCalls` | Explicit per-terminal and per-route permission; must be enabled when the authorization claim is first created |
| `CardPayments__ShadyBankAuthorization__Bindings__0__TerminalClockOffsetMinutes` | Verified terminal-local offset from UTC for matching the reported call start |

The host durably claims a quote for its original request type and call sequence before invoking the bank. The same quote and request reuse the bank UUID across reconnects; different sequences cannot reuse the quote. Same-socket RETRANS replays the cached response. A timeout, HTTP error or malformed bank decision declines the terminal and is separately audited. A timeout is not proof the remote reservation did not occur; it must be reconciled before settling or releasing funds.

For the optional legacy MT2 binding, a normal recent terminal quote still takes precedence. If no quote exists, CoinLine resolves the effective published host rate plan for the actual bound route, requires an allowed positive initial charge, and records that price and version in a separate durable authorization sequence claim. It does not create an MT63 or call record. The same terminal, route and sequence keep one reservation UUID through retries, reconnects and later terminal quotes. An expired or ambiguously reused sequence is declined rather than charged again. This conservative mode is only for isolated synthetic routes whose terminal behavior has been reviewed. It is not a general card-payment fallback or a way to bypass the bank balance check.

An approval does not post a CoinLine payment or debit its ledger. The bank's reserve-only decision and subsequent capture are separate. The current terminal credential recognizer is restricted to the existing synthetic magnetic-card fixture. The generic bank client accepts only opaque instruments and is reusable for independently validated smart-card applications; this does not establish historical Proton, stored-value or other issuer application acceptance. Those paths require their own qualified application contract and outcome evidence.

## Optional call-detail capture

The optional worker uses the bank's scoped `/api/merchant/capture` endpoint on the same configured origin. Enable the separate bank capture capability and its additive database migration first. Enable both Manager switches above only for an independently qualified terminal and reserved route, with its actual clock offset. Previously created authorization claims are not retroactively eligible.

An eligible upload is a complete, positively charged MT53 credit-card call record with full destination, duration, terminal time and call sequence matching one recent approved reservation. The actual reported amount must equal the reserved charge and the duration must be within the authorized period. A missing, zero, ambiguous, unanswered, unrelated, stale or larger amount never creates a posting intent. An NCC upload still receives its normal acknowledgement independently of the bank request.

The Manager retains one durable posting intent per authorization and per uploaded record. It sends only the reservation UUID, settlement UUID and amount; the bank posts at most once for that identity. The worker retries an uncertain response with the same settlement UUID and a bounded deadline, and leaves permanent failures or exhausted retries for reconciliation. A valid matching bank receipt marks the intent posted. There is no second debit to CoinLine's local card ledger. The Payment Transactions page has a separate ShadyBank call payments section showing the reported charge, receipt status, attempt count and references to the retained authorization and uploaded record. An unresolved receipt is not proof that the bank did or did not post; inspect the bank before any manual action.

The automated regression uses real PostgreSQL and an in-process merchant HTTP fixture. An additional explicit lab test can contact an isolated loopback bank using `COINLINE_SHADYBANK_LAB_SETTINGS` (private JSON with `merchant_service_key` and `instrument_token`), `COINLINE_SHADYBANK_LAB_URL`, `COINLINE_SHADYBANK_LAB_RESULT` (sanitized request ID and outcome) and the disposable PostgreSQL test connection. It is skipped by default. Use an independent synthetic account and reconcile or release the resulting reservation after the test.

For an independently funded synthetic bank capture bench, the separate `Isolated_real_bank_posts_one_matching_synthetic_call_fixture` test also requires `COINLINE_SHADYBANK_CAPTURE_LAB=1`. It accepts an isolated trusted HTTPS bank endpoint (or explicit loopback lab HTTP), sends a synthetic five-cent TCP call-detail fixture after authorization, repeats the upload, and records the matched bank receipt identifier. Run this test alone with a disposable database and synthetic instrument, then verify the bank's posted and available balances and single purchase. It is not a native terminal capture or a general-purpose bank transaction tool.

The isolated real-bank bench passed a five-cent native-shaped TCP authorization and exact reconnect replay. The bank retained one masked reservation, the posted balance and CoinLine payment ledger remained unchanged, and the ordinary bank void operation restored the full synthetic available balance. This is a TCP fixture and real bank service qualification, not a physical or emulated terminal payment acceptance claim.

A separate native MTR 1.9 two-line emulator run on an independent synthetic terminal subsequently passed cold installation (11/11 table acknowledgements), warm service, magnetic-card acceptance, and a genuine 39-byte MT2 without a preceding MT63. The legacy binding derived the five-cent initial charge from its published plan and ShadyBank approved one reservation. The terminal outpulsed the complete reserved local-only destination, received answer supervision and returned on hook. The posted synthetic balance remained USD 1.00, the available balance was USD 0.95, and no purchase was posted. After normal exit, the ordinary bank void operation restored USD 1.00 available. No uploaded CDR was observed during this test, so neither native settlement nor physical hardware acceptance is established.

A later run retained that terminal's normally saved state and installed only two reviewed collection records, MT34 and MT35, on an ordinary Craft refresh (2/2 application acknowledgements, Completed 02). The next synthetic magnetic call produced a distinct five-cent authorization, local answer and normal hangup. A normal Craft call-record upload then reported **Completed 00** and the Manager stored two genuine MT53 records with distinct durable keys, the exact normalized reserved destination, credit-card payment classification, ten- and eleven-second terminal-reported durations, and zero in both reported amount fields. The retained raw upload data was empty. A subsequent warm Craft check displayed **No call records**; the count remained two. The second authorization was separately voided, both reservations remained voided, and the posted and available synthetic balance returned to USD 1.00 with zero pending reservations and zero purchases.

This establishes native magnetic-card authorization and ordinary CDR upload, not a matching charged CDR or permission to capture funds. In particular, the zero reported amounts must not be replaced with the authorization amount merely to create a payment. The optional capture path remains disabled by default. A positively charged native call and its matching bank receipt, smart-card application and physical-terminal qualification remain pending.
