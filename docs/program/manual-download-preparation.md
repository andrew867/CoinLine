# Manually selected phone download preparation

The legacy manager offered a selection list for packing the existing configurations of up to forty individual terminals, rather than requiring the operator to choose a single source configuration for all of them. Prepare-now and dated host preparation were distinct from the terminal making contact and acknowledging the tables.

CoinLine's Downloads page supports search by phone ID or name, a removable list of up to forty distinct phones, and immediate or future UTC preparation. Choose **Full assigned configuration** (the default) or **Selected records only** to prepare the same chosen message types from each phone's own published assignment. The latter includes each selected record's declared data dependencies in the correct order. This does not copy records from one phone's set to another.

A read-only preview shows each phone's published assignment and exact record list, including any dependencies. A missing, ambiguous, incompatible or invalid selected record blocks that phone; resolve the issue or remove the phone before reviewing again. All selected phones must be eligible. The confirmation compares a deterministic snapshot of the requested scope, assignment and record identities with the reviewed selection, and commits the schedules together. It does not change assignments, replace existing pending work or schedule firmware parameters. Immediate preparation creates each full or partial batch before phone contact. Future preparation pins the reviewed published set and record selection until the scheduled worker packs it. Selected schedules are collected during routine call-in or callback; a manual Craft refresh is a separate workflow. Mandatory installation and memory recovery continue to use the full assigned configuration.

| Workflow | Editor/console | Host preparation/encoding | Terminal acknowledgement | Behavior |
| --- | --- | --- | --- | --- |
| Manually selected phone list | Search, add/remove, review, explicit preparation time, confirmation and batch links | Reuses validated assigned records and the existing scheduler; no new record format | Two real PostgreSQL-backed loopback NCC sessions delivered their respective full synthetic records byte for byte, and each MT14 was recorded on the originally prepared batch; no third phone was scheduled. | Stock phone and physical bench validation remain separate |
| Selected records across assigned sets | Select named message types, review per-phone dependencies, explicitly confirm | Retains exact published set and selected types in each partial schedule; rejects missing types and operational or scheduler messages | See selected-record regression below. | Stock phone and physical bench validation remain separate |

## Verification

- Isolated PostgreSQL integration: seven tests passed across list preparation, table permissions and account access. The list tests verified different assigned sets, exact version identities and record bytes, no write at preview, competing confirmations (one accepted, one conflict), stale assignment and preparation-time rejection, inactive/missing/unassigned phone handling, and future worker preparation of the originally reviewed set after an assignment changed. The two immediate schedules completed over real loopback TCP with application acknowledgements; physical firmware remains untested.
- WebUI: ten focused Vitest tests passed, including four list-preparation tests. The page does not request denied registers or download history for an Add-only operator. Chromium verified the distinct assigned configurations, removal of a blocked phone and confirmation of the exact remaining list; the existing failed-download browser regression also passed. The production web build passed.
- Selected-record regression: two phones with distinct published configurations requested only MT29. The first partial batch included its required MT50 before MT29; the second contained only its own MT29. Both received their exact synthetic bytes over routine loopback NCC contact and completed the original prepared batch with application acknowledgements, without sending unrelated records. A future partial schedule was also prepared from the pinned set after the phone's assignment changed. Tests reject missing records, changed scope and operational/scheduler requests without scheduling anything.
- Selected-record WebUI: five focused Vitest tests, production build and three local Chromium flows passed, covering both full and selected preparation and the failed-download review. A stock-terminal or physical bench run of this particular mixed-list workflow remains pending.
