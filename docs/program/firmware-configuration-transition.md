# Firmware upgrade configuration review

Firmware jobs includes a read-only configuration transition review. Select a phone, a registered target firmware version and, optionally, an independently prepared configuration set explicitly targeted to that version. The review compares the phone's assigned record lengths with the target profile and the supplied target records. It neither changes an assignment nor requests a device action. Operators need read access to firmware jobs, the firmware registry, phones, table sets, table records and assignments because the review combines those screens' data.

The comparison also checks the candidate against the documented legacy table families for the registered terminal type. Use **Review a different target terminal family** to compare an explicitly chosen family without altering the phone's registered type. Missing, partial or unidentified mandatory families are highlighted for review before staging. Feature-specific families are displayed separately, and available candidate records link directly to their editors. The documented active screening count and the verified packed target layout may differ; the checklist does not establish actual mandatory records, native behavior or upgrade compatibility.

For identified earlier-to-later profiles, the comparison distinguishes renamed configuration families from unsupported or unknown records. MT22 to MT134, MT23 to MT135 and MT27/28 to MT85/86 are shown as replacement-family reviews only when the candidate has the verified target shape. A supplied replacement does not establish semantic conversion. Earlier single-compressed local dialing segments are compared against actual later double-compressed areas and MT73 tuples for every exchange. An active source area is considered equivalent only if the saved target contains an unambiguous matching area and the complete tariff tuples agree. Missing areas, different charges or unknown retained data remain preparation findings. Links open the exact target record for review.

The table identifies records that need replacement, missing source features, same-length fields that need layout confirmation, new target records and known target records whose applicability has not been established. A missing record type in an incomplete catalogue is unknown, not proof that the feature was removed. A catalogue of acknowledged records is not a list of mandatory records.

## Example: MTR 2.0 to MTR 2.11

The retained configuration evidence establishes these differences between the earlier and later Multi-pay profiles. The earlier profile's recorded INSTALL did not reach service. Neither profile alone establishes a compatible remote image transition.

| Record | Earlier MTR 2.0 length | MTR 2.11 class length | Configuration review |
| --- | ---: | ---: | --- |
| MT21 management access | 18 | 48 | Target-specific record required, including independently reviewed new fields. |
| MT26 feature options | 72 | 72 | Same length; field layout must be independently confirmed. |
| MT92 screening | 3,401 | 3,061 | Review the 200 to 180 entry change, order, and any entries exceeding target capacity. Do not truncate. |
| MT62 numbering plan | 353 | 353 | Earlier display formatting occupies 132 bytes and the last eight bytes are currency settings. Later display formatting occupies 140 bytes. Do not copy equal-length records wholesale. |
| MT22 and MT23 earlier card and carrier data | 661 and 678 | Unknown for this target profile | Review the target card and carrier records and preserve intended acceptance and routing. |
| MT134 and MT135 later card and carrier data | Unknown for the earlier profile | 1,153 and 1,109 | Prepare target data; a length match does not prove card or route behavior. |
| MT85 and MT86 later visual prompts | Unknown for the earlier profile | 8,001 each | Confirm whether applicable and [review selected messages from MT27/28](firmware-visual-prompt-transition.md) into prepared target records. |
| Local dialing segments, MT101 to MT115 versus MT136 to MT149, MT154 and MT155 | 403 per segment | 203 per segment | Both layouts cover 800 exchanges; the later record has only four tariff indexes. Convert each active area using exact target MT73 local tuples, never by truncating source indexes. |

Source and target configuration should remain separate. Do not activate target records against the installed source profile, or edit the phone's registered firmware simply to enable a download.

The terminal setup carry-forward prepares MT26 (features) and MT31 (install and service) together. Their record lengths are equal across the identified profiles, but the draft carries only named, identically packed common fields; target-only fields and spare bytes retain their original values. Common operator access pointers are mapped to configured target MT92 entries with matching shared call classification, pattern and rate/carrier meaning, including an exact MT73 tuple for rated entries or the same uniquely configured carrier for a free Feature Group B reference. An ambiguous match requires an explicit selection, and missing or incompatible rules block preparation. The earlier incoming-call rate, operator/toll conversion, and default language slot are not reinterpreted as later language/routing or preauthorization fields. The operator must review these differences before saving. Configured source Craft and desk key-card fields may be carried without displaying their values, or the prepared target values may be retained; unrecognized differing source credentials cannot replace target credentials. Predial strings are also protected in the preview. The server-keyed review stamp binds both records, companion records and review choices without publishing field values or a proposed-payload digest; the response is not cached. Later packet-data predial, analog prefix, cashbox-query and Craft reporting options are retained. The graphical target defaults to retaining its prepared display and advertising settings. No assignment, firmware job, download or activation is created; actual target behavior remains to be verified.

The reviewed MT73 carry-forward stages the common earlier classifications and signed period/unsigned charge tuples into a separate later candidate. It groups equal source rows, reuses exact existing target tuples, and proposes new allocations only in canonical empty invalid/unavailable positions. The candidate's local index domain 0 through 3 and the numeric tariff references in included screening, quick-access, later graphic, stored-value discount, area, international and local-exchange records remain protected. Other active or noncanonical target tuples are not overwritten. Unreviewed included records prevent allocation; absent companion records remain explicitly unknown. The preview identifies the source-to-target mapping to use in subsequent configuration migration; candidate header, date and all other records remain unchanged. Actual rating behavior is not established by a matching tuple or draft.

## Qualification sequence

The [common configuration carry-forward](firmware-common-control-transition.md) reviews MT29, MT30, MT32, MT34, MT35, MT50 and MT58 in independently selected groups. The candidate's reserved bytes, one-time clock adjustment, unselected hardware calibration and separate restricted-route references are retained. Coin settings, reporting modes, service restriction schedules and later device behavior require separate review; creating a draft does not qualify the upgrade.

1. Identify the exact installed hardware family, installed version, target version and approved compatible image. Record the source assignment and effective records, including protected per-phone settings without recording their values in public evidence.
2. Prepare a separate candidate configuration using proven target layouts and deliberate conversion rules. Validate required records, preserve supported site settings and verify each intended change. Resolve outstanding downloads before scheduling.
3. Qualify the native scheduled call, independent code-server connection, carrier, protocol exchange and image integrity with an isolated test terminal. Test interrupted transfer and recovery before permitting an upgrade on an operational terminal.
4. After the upgrade, verify the device actually reports the target version before applying the prepared configuration. Record the exact selected download and acknowledgements; neither a scheduled job nor an acknowledged code schedule proves an installed version change.
5. Verify normal warm service, free and rated calls, relevant payment and feature behavior, routine reports and recovery. Repeat on physical equipment before representing the transition as hardware-qualified.

The management-access carry-forward prepares a separate target draft using the source's registered identity and canonical manager numbers in the identified 18- or 48-byte MT21 layout. The target candidate supplies its own ADSI identifiers and reserved data. The conversion rejects noncanonical terminated numbers, missing primary access, mismatched identity, unqualified lengths and values too large for the shorter layout. The preview returns counts and a revision-bound token, not access values.

The numbering-plan carry-forward separately reviews ordinary MT62 header settings, the linked dialing graph and the display-format graph. Source nodes are copied at their original relative positions, including verified links, while only recognized candidate nodes are replaced. Nonzero unassigned source bytes remain in the source; unknown candidate bytes are retained and a conflicting source node blocks preparation. Circular fallback and unrecognized graphs block the selected conversion, and a blank earlier dialing graph cannot silently remove an active candidate plan. The earlier currency tail is never copied into the later eight-byte display-format extension; a selected replacement retires candidate nodes in that extension, not unassigned bytes. The operator can independently retain the target header or either graph, with the graphical profile defaulting to retaining its prepared format. Target stored-value discount fields and other site bytes remain unchanged by default, and explicit desk key-card carry-forward is protected. The earlier answer-supervision, manager-timeout and currency fields require later-profile review rather than positional copying. The preview lists field actions, graph sizes, preserved-byte counts and findings without exposing route patterns or credentials; the server-keyed stamp binds the selected choices and both configurations. No live assignment, download or firmware action is created.

The screening carry-forward projects the common fields and descriptions from the 200-entry MT92 into positions 1 through 180 of the later candidate, including blank and vacant positions. It does not truncate or reorder populated or reserved overflow, reinterpret source spare bits as later-only flags, or overwrite a changed target position with active later-only options without resolution. For source tariff references, target MT73 tuples must match exactly; ambiguous matching indexes are reviewed explicitly. For source free Feature Group B carrier references, the target carrier identifier must be uniquely assigned in the prepared MT135, and the operator must review companion carrier behavior. Existing source references beyond capacity block conversion, and changed positions referenced by the target companion records produce review findings. Every other candidate record remains byte-for-byte unchanged. Registered observed-length-only profiles still require actual device qualification. The preview binds source, candidate, reference choices and retained record contents without exposing route digits or description text.

The local dialing carry-forward matches each used source MT73 tuple exactly within target indexes 0 through 3 and preserves all other tariff bytes. It groups active source areas into same-area or fully vacant existing target segments, reports changed codes and tuple differences, and rejects duplicate areas, noncanonical disabled destinations and insufficient capacity. A source tariff without an exact local target match blocks preparation until the candidate is independently reviewed and corrected. Omitted source/target segments remain unknown and are never treated as blank. This draft can be reviewed with the screening and management-access drafts; actual device lookup and rating remain unqualified.

The carrier carry-forward uses the identified earlier MT23 and later MT135 layouts together with both profiles' magnetic-card and screening records. It retains carrier identifiers, matches existing candidate rows by identifier, and allocates new rows only in completely blank carrier positions. It carries common default carrier selections, shared carrier fields and both accepted and rejected magnetic-card bits into reviewed target card positions. An active Feature Group B screening pointer must refer to a matching configured target rule. Duplicate identities, ambiguous mappings without an explicit selection, unknown card applications and insufficient capacity block the draft. The later-only defaults, rate-permission field, reserved bytes, unrelated carrier rows and unmapped target card positions remain unchanged. Review the separately prepared card service/validation settings and screening rates before using the new draft. The operator sees positions and findings rather than card ranges or route digits. This is configuration preparation only, not qualification of actual carrier selection or card acceptance.

The optional combined card and carrier preparation carries eligible MT22 magnetic ranges and common validation fields into MT134, then stages the corresponding MT135 carrier configuration in the same unassigned draft. Existing target card positions are reused only for exact range, standard and selected carrier matches; otherwise a completely vacant position with no existing active carrier acceptance is required. The relative source selection order is preserved, unrelated target ranges and later-only card settings remain unchanged, and newly allocated positions retain the vacant template's later-only settings. The earlier ten-position service-code list must fit the later five-position list with canonical, contiguous entries; extra data is not truncated or reinterpreted. Overlapping unrelated ranges, duplicate identities, reversed order, noncanonical ranges, unsupported source applications and insufficient safe positions require operator resolution. Target master links are detached only for modified card rows, retaining unrelated links. Both record revisions and digests are bound to the preview along with the candidate and preparation mode. This does not establish stored-value application acceptance, new validation settings or live provider behavior.

### Quick-access key carry-forward

Prepare MT55 only after choosing the physical source and target button layouts. The five-key layout occupies positions 6 through 10 of the full ten-position, 571-byte record; the ten-key layout uses all positions. Shared positions retain their destination, two display lines, customer reference and common call settings. Paid references require an identical MT73 tariff tuple, and free Feature Group B carrier references require an explicit reviewed target carrier. Positions beyond the target's capacity are not moved or silently truncated. Inactive source positions are not promoted to active target buttons, and additional candidate positions stay unchanged. Earlier change-card and messaging behavior and changed target keys with later-only flags require manual review. Candidate reserved bytes and unrelated records remain intact. The preview identifies changed, cleared and retained physical positions and binds the reviewed choices to both configuration revisions. Review retained service-restriction and graphical-menu references separately. The result is an unassigned draft, not a device action or remote-upgrade qualification.

The PostgreSQL staging regression verifies the key-6 tariff remap, unchanged extra target keys and companion records, stale-preview rejection, read-only permissions and no change to the original phone. A separate target fixture acknowledges only the exact selected MT55 on the queued batch after explicit publication. Native button, routing, display and physical acceptance remain pending.

Remaining record migration, automatic activation staging, actual code delivery, post-reboot target-version confirmation, and service qualification remain separate work. The earlier observed code-server connection exchanged no application bytes and did not change flash. No upgrade compatibility pair has been qualified by this review.
