# Visual prompt preparation during a firmware transition

In **Firmware jobs**, compare the installed phone's published configuration with a separately prepared target configuration. If the recognized earlier 140-row language records and later 400-row records are present, **Prepare visual prompt languages** compares MT27 with MT85 and MT28 with MT86 independently. It does not create missing language records or assume that a known length proves the target display behavior.

The review pairs messages with the same identified meaning. Common positions keep the corresponding message number. Earlier emergency-service message 28 maps to later emergency-service message 70, not later message 28 (out of service). Earlier positions 0, 1 and 51 through 55 are left unmapped because their meanings differ or are unassigned. Additional later messages, months, softkeys and any unchecked rows remain as supplied in the prepared target.

Choose individual two-line messages after comparing the source and target text. A blank source line clears target text only as part of an explicitly selected message. Unmapped display cells in either source or destination make that message unavailable for this carry-forward; review such text in the individual prompt worksheet. Equal visible text retains the candidate's exact padding. A changed readable line is copied as its complete twenty-cell field, without re-encoding or moving any other row. The preview reports how many bytes would change and requires a fresh review after changing the selection.

Create a separate unassigned target draft only after reviewing the text and remapped positions. Both configurations, the complete candidate record list, selected message IDs, registered phone and target identities are bound to the server-keyed preview. Other candidate records retain their exact bytes and revisions. Authorized readers can compare the prompt text; audit events retain only the selected positions and changed byte counts, not the text. No assignment, download, firmware job, publication or terminal action is created.

This is a host-side conversion of identified message positions, not an assertion of native upgrade compatibility or language-selection behavior. Review the remaining target settings, then qualify the downloaded prompts and actual device display independently.

An offline review of four retained demonstration prompt records confirmed their lengths and manifest digests, and unchanged native editor saves preserved every byte. In the first language, 59 of 63 mapped message pairs had identical visible text and four differed; in the second, 61 of 63 matched and two differed. The emergency-service wording was present in both the earlier and later mapped positions in each language. Selecting the differing readable pairs changed only their intended target cells (72 and 57 bytes respectively); a repeated projection was unchanged. No prompt payload or text is included in this report.

The three packed unit tests and isolated PostgreSQL staging regression verified unknown glyphs, unmapped positions, missing target languages, stale reviews, independent permissions, exact draft bytes and unchanged original configurations. In a separate explicit test, the finished draft was published and queued for a registered later-profile loopback NCC fixture. Exactly MT85 and MT86 were delivered with their expected synthetic bytes, both MT14 results completed the original partial batch, and the earlier source phone received no download. Eleven focused WebUI tests, the production build and the two Chromium prompt and tariff transition flows passed. Native terminal and physical display qualification remain pending.
