# Authoring operational parameter records

When a draft lacks feature and call options (MT26), user interface parameters (MT30), installation and servicing parameters (MT31), or modem parameters (MT33), the native editor can create the missing record from explicitly entered settings. Use an independently reviewed compatible record copy instead when actual operating values are already known; the authoring form does not supply a substitute for a validated terminal configuration.

1. Open the relevant configuration panel in an unpublished set and select the missing record. A registered target with a confirmed layout offers that exact profile. An untargeted draft offers a deliberate choice among the identified layouts. Observed-length-only targets and unsupported formats remain import workflows.
2. Complete the settings section by section. Required choice fields and switches initially have no selected value. Numeric fields retain their documented units and limits. Use **Set unentered switches to Off** only when that is the intended setting; it never replaces a switch already set explicitly.
3. Optionally paste a JSON object keyed by the named fields. Review the supplied values and their effects on entered settings before applying them. Unknown keys or values outside the supported ranges are rejected. Unspecified fields stay as entered and remain required if unset. Use quoted keypad strings and explicitly choose **Use no digits** for an empty predial. Do not paste protected configuration values into the review JSON; MT31 has separate password fields for these.
4. Create the record once all known non-spare settings have explicit valid values. The form saves a new draft record and opens the existing native editor. Unassigned bits and spare bytes in a newly created record start at zero. Review any applicable spare values using the ordinary editor.

The earlier and later MT26 and MT33 layouts remain distinct, including language and modem timer fields with different meanings at the same offsets. MT30 uses its identified 68-byte layout for both supported families. A profile choice does not convert entered settings to another layout; values are kept separately while the form is open.

MT31 uses separate 37-byte earlier and later layouts. The later profile exposes cashbox querying, deferred Craft reporting, packet-data predial and the analog mode prefix; the earlier profile retains the corresponding spare positions. Explicitly enter the required configured access and key-card values in their own fields, even when copying other settings from a review. Creation has no prior credential to preserve and does not invent a disabled value. The ordinary typed record view continues to return no protected value. A blank edit of an existing protected field is not needed to preserve it; leave it unchanged.

Creating an operational record does not register a terminal, assign a set, publish it or initiate a download. A structurally valid record does not demonstrate workable call timing, payment behavior or modem supervision. Review the actual site configuration and dependencies before publication and retain separate terminal acknowledgement and behavior evidence.

Isolated PostgreSQL tests created all four records for both supported target profiles and matched independent byte expectations. Unchanged modem and installation saves retained their revisions and digests; edited answer-removal and retry settings changed only the intended bytes. Earlier spare positions and protected values remained independent. The typed response did not disclose protected values, and creation rejected credentials mixed into ordinary settings. No assignments or download batches were created. Browser tests verified reviewed named settings, explicit switch and blank-digit choices, profile isolation, required values, failed-create recovery, separate protected input and read-only access. These are host-side authoring and encoding results, not new terminal acknowledgement or behavior evidence.
