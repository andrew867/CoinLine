# Authoring operational parameter records

When a draft lacks feature and call options (MT26), user interface parameters (MT30), installation and servicing parameters (MT31), modem parameters (MT33), or numbering and display formatting (MT62), the native editor can create the missing record from explicitly entered settings. Use an independently reviewed compatible record copy instead when actual operating values are already known; the authoring form does not supply a substitute for a validated terminal configuration.

The reference record catalogue labels these confirmed layouts as **explicit authoring (no default template)**, independently of the observed firmware acknowledgement and behavior columns. It also recognizes the existing dedicated twenty-slot MT29 text advertising creation workflow. An observed record length alone does not establish a usable authoring layout.

1. Open the relevant configuration panel in an unpublished set and select the missing record. A registered target with a confirmed layout offers that exact profile. An untargeted draft offers a deliberate choice among the identified layouts. Observed-length-only targets and unsupported formats remain import workflows.
2. Complete the settings section by section. Required choice fields and switches initially have no selected value. Numeric fields retain their documented units and limits. Use **Set unentered switches to Off** only when that is the intended setting; it never replaces a switch already set explicitly.
3. Optionally paste a JSON object keyed by the named fields. Review the supplied values and their effects on entered settings before applying them. Unknown keys or values outside the supported ranges are rejected. Unspecified fields stay as entered and remain required if unset. Use quoted keypad strings and explicitly choose **Use no digits** for an empty predial. Do not paste protected configuration values into the review JSON; MT31 has separate password fields for these.
4. Create the record once all known non-spare settings have explicit valid values. The form saves a new draft record and opens the existing native editor. Unassigned bits and spare bytes in a newly created record start at zero. Review any applicable spare values using the ordinary editor.

The earlier and later MT26 and MT33 layouts remain distinct, including language and modem timer fields with different meanings at the same offsets. MT30 uses its identified 68-byte layout for both supported families. A profile choice does not convert entered settings to another layout; values are kept separately while the form is open.

MT31 uses separate 37-byte earlier and later layouts. The later profile exposes cashbox querying, deferred Craft reporting, packet-data predial and the analog mode prefix; the earlier profile retains the corresponding spare positions. Explicitly enter the required configured access and key-card values in their own fields, even when copying other settings from a review. Creation has no prior credential to preserve and does not invent a disabled value. The ordinary typed record view continues to return no protected value. A blank edit of an existing protected field is not needed to preserve it; leave it unchanged.

MT62 uses the identified 353-byte layouts. Enter digit collection, payment classification, rate-response mapping and other named settings independently of the rules. The earlier profile exposes currency display and voice settings, with 132 bytes available for display-format rules. The later profile has 140 bytes for those rules and does not expose the earlier currency tail. Both have 180 bytes for dialing rules. Use the linked-rule editor to create at least one complete dialing rule, then create display-format rules or deliberately choose **Leave display formatting empty**. A new graph rejects unknown digit codes, unassigned classifications, broken or circular links, and rules that exceed the target's packed space. A reviewed existing imported record is still edited through the existing preservation-aware workflow rather than re-created from defaults. The key-card configuration value is entered separately, not in reviewed JSON.

For ordinary paid service, review the payment class of broad destination rules as well as the rate table. A broad local or toll rule marked **No payment** can allow calls without collecting the intended tariff. The editor and configuration review flag that combination, including an entirely unset host-rate response map, as advisory findings. A free-only service may intentionally use that classification. Do not use broad free classifications as a substitute for exact free-service screening entries; validate regular paid calls independently of free calls.

Creating an operational record does not register a terminal, assign a set, publish it or initiate a download. A structurally valid record does not demonstrate workable call timing, payment behavior or modem supervision. Review the actual site configuration and dependencies before publication and retain separate terminal acknowledgement and behavior evidence.

Isolated PostgreSQL tests created all five records for both supported target profiles and matched independent byte expectations. Unchanged modem, installation and numbering saves retained their revisions and digests; edited answer-removal, retry and response payment settings changed only the intended bytes. Earlier spare positions and protected values remained independent. The typed response did not disclose protected values, and creation rejected credentials mixed into ordinary settings. No assignments or download batches were created. Browser tests verified reviewed named settings, explicit switch and blank-digit choices, profile isolation, required values, failed-create recovery, separate protected input, complete graph and formatting decisions, and read-only access. These are host-side authoring and encoding results, not new terminal acknowledgement or behavior evidence.
