# CoinLine configuration and terminal parity matrix

This is the current acceptance summary for the management console and terminal configuration catalogue. A message type (MT) identifies a record on the management link. A byte count includes the message type where a complete record length is known.

An editor, valid encoding, a terminal acknowledgement and observed device behavior are four different milestones. An acknowledged record does not prove its feature works. A synthetic TCP fixture is not an emulated terminal, and an emulated terminal is not a physical terminal. Unknown layouts remain available for controlled binary import rather than being treated as verified typed fields.

The later type-40 graphical catalogue has native application acknowledgement evidence for all 45 registered record types across separate transfers. A single complete 43-record transfer on 2026-11-27 matched every retained published payload hash and profile length, received 43 MT14 results, and ended with terminal clear and peer release. This includes both primary visual-prompt records, text and graphical advertising, all sixteen double-compressed local-dialing segments, MT150 through MT152, and the collection, feature and carrier settings. MT58 and MT94 were not part of that transfer. Separate [enabled and disabled MT94 transfers](code-server-observation.md) each received application acknowledgement. The independent [MT58 service restriction test](service-restriction-native-qualification.md) subsequently acknowledged its selected 26-byte enabled and disabled records, demonstrated paid-call denial with the free control retained, and restored the paid prompt after a normal restart and selected refresh. This establishes delivery of all registered graphical records, not universal edited feature behavior or physical acceptance. A separate [regional rating qualification](regional-rating-packages.md) verified a selected MT73/92 transfer, paid local and national initial charges, a local answered quarter call and tested free routes. The 711 and 811 service codes, seven-digit pre-payment prompt, later-profile paid continuation and physical acceptance remain unqualified.

The Table definitions reference catalogue now scopes observed behavior to the selected registered profile and counts it separately from editors, authorable records and application acknowledgements. Observed-length-only profiles do not inherit the behavior of another terminal with a matching record size. An acknowledged MT133 remains without a specific behavior observation, and MT94 schedule acknowledgement and network connection remain distinct from completed code transfer.

For the two listed import-only layouts, the record editor and catalogue now expose [partial field coverage](operational-record-authoring.md), including retained byte ranges and bit masks. Unknown fields remain uneditable, and existing payloads are required. Complete field mappings and matched terminal evidence remain outstanding.

The [MT93 and MT134 operator guide](mt93-mt134-operator-guide.md) explains the earlier and later editors, card acceptance, discount selection and related configuration. The MT93 credential-preservation regression uses noncredential synthetic sentinel bytes. Ordinary unit-limit, rebate or later discount edits and blank protected fields retain the complete opaque credential region in both layouts. Real PostgreSQL verifies the saved record bytes and read-only credential fields; three isolated NCC fixtures acknowledge the exact selected older, later standard and graphical records. These checks do not establish a stored-value issuer or payment application.

## Acceptance rule for future edits

The [carrier reference review](carrier-reference-review.md) identifies default selections, selected card ranges and free Feature Group B references in the earlier and later carrier editors. It distinguishes the carrier identifier from the row position, keeps card-acceptance bitmaps separate, and reports duplicate or unavailable records. The review is not a test of actual carrier selection on a call.

The [operational-record authoring workflow](operational-record-authoring.md) creates missing MT26, MT30, MT31, MT33 and MT62 through explicit named settings. Both confirmed profiles passed exact-record PostgreSQL creation, unchanged saves and one-byte modem timer, installation retry and numbering response-payment edits. MT31 and MT62 separate protected values from ordinary settings; MT62 requires a complete dialing graph and explicit formatting choice, with profile-specific capacities. Broad ordinary no-payment rules are advisory review findings, not automatic changes. The existing native editors retain spare-field review. These authoring checks do not establish new terminal acknowledgement or actual feature, timing, servicing, routing or modem behavior.

The download detail view now reports retained record acknowledgements, terminal clear and transport-release observations separately from terminal service. PostgreSQL and browser fixtures verify that a completed batch cannot by itself produce a service confirmation, and that a failed batch identifies the exact missing record. Actual INSTALL and service behavior remain independent acceptance steps.
