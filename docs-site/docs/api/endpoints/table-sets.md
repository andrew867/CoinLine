**Route prefix:** `/api/tables`

The assignment API supports `terminal`, `group`, `site` and `customer`. Apply the same `targetType` and `targetId` with the preview's eligible phone IDs in `terminalIds`. A changed eligible list requires another preview.

A new set accepts an optional `targetFirmwareVersionId`. A draft copy inherits the target. Published targeted sets can be assigned and downloaded by phones with the same registered firmware version. Detail responses expose `firmwareFindings`. Blocking findings prevent publishing. Other findings identify records whose format still needs verification.

Table set details also report `tableProfileEvidence`, including the known record-length count, the count acknowledged on OEM emulated firmware, and whether the full compiled catalogue is identified. Targeted sets with a complete catalogue reject absent message types. NCC pickup checks the registered phone's record lengths and complete-catalogue membership even for an untargeted set. A rejected batch retains its failed items and sends no table records.

The family review describes the full installation table families from the archived Manager reference. Each row includes its candidate message types, the records present in the saved set and their format evidence. The documented screening count and packed editor capacity are reported separately. A known target length is stronger evidence than a recognized editor layout. A graphical record group is marked partial when fewer than its three records are present. Inmate configuration families remain unmapped until their wire records are identified. The review is advisory for partial downloads and never changes the target firmware or the assignment.

The record-copy request takes `sourceSetId`, `sourceRevision`, `destinationRevision` and a `recordNumbers` array of decimal message types. Read each revision from the table set detail response. Submit the same request to the preview and apply endpoints. The response lists each planned record as `add`, `replace` or `keep` and marks automatically included dependencies with `required`. Copies write to drafts and require a global source set or one belonging to the same customer. A changed source or destination revision returns HTTP 409 and requires a new review.

For selected-record assignment updates, the route identifies the published source set. Send `targetType`, `targetId`, `sourceRevision`, `copyRecords` and `removeRecords`. The two arrays contain decimal message types and can each be empty. The preview reports each phone's current set, planned actions, skipped reasons, and the count of assignments and resulting sets. Add its `previewToken` to the same request on confirmation. Changed scope membership, assignments or configuration require another preview. The update saves the resulting published sets and assignments together and retains the previous sets for rollback.

If MT21 is explicitly in `copyRecords`, `personalizeAccessIdentity: true` replaces only its five wire-ID bytes at offsets 1..5 with the target phone's registered ten-digit decimal identity. The default remains false. The source record must have the verified 18-byte or 48-byte layout and match any known registered firmware profile. The preview marks the per-record action with `personalized: true` and reports a separate set for every changed phone. Confirming an altered flag with the old token returns HTTP 409. The source and previous assignments are immutable, unrelated records are carried forward, and repeating an unchanged update yields zero changed assignments. The apply response identifies each resulting personalized set with `phoneId` and `phoneDisplayName`. The operation does not queue a download. A paused run keeps its original reviewed identity and blocks a phone whose registered wire ID changes.

Set `stopOnIssue` to `true` to process a recoverable rollout in terminal ID order. An optional `beginWithTerminalId` starts at the specified terminal in the reviewed scope. The preview returns the changes that can be saved before the first issue and the count waiting for recovery. Include its `rolloutId` with `previewToken` when applying. The response includes the saved rollout status, counts, and the blocked phone and reason when paused. Repeating the same confirmation returns the saved status.

To continue a paused rollout, send its current `revision` and `decision` of `retry`, `skip`, or `stop`. Retry reevaluates the blocked phone and the remaining reviewed phones. Skip records that phone as skipped and continues from the next one. Stop closes the rollout with its completed changes in place. Newly matching phones require their own preview. A stale control revision returns HTTP 409. Assignment changes and the cursor are saved together on each attempt.

The recognized Multi-pay profile permits removing records documented as optional. The preview reports any dependency that prevents removal. Removal changes the assignment for future downloads. Delivery of a set without the record can leave previously installed terminal data in place.

For the verified 200-entry Multi-pay profile, the set review checks MT92 screening rules that use a direct tariff or mark a call as free. If screening or configured MT101 exchange rules refer to tariffs without an MT73 record in the set, the review returns a warning so a partial update can rely on the phone's installed tariff record.

Each advertising slot has `text`, `durationTicks`, `mode`, `blankBefore` and `endSequence`. Set `endSequence` to write a leading zero that ends the current rotation. To show a timed blank, send empty `text` with `endSequence` false and a positive duration. The response includes `onHookEnabled`, `quickAccessEnabled`, `callEstablishedEnabled` and `scrollTicks`. The settings are null when the respective record has no recognized layout. Durations and scroll values use 10 ms ticks.

Each slot also returns `spareByte` (0 to 255), `reservedFlags` (a mask of attribute bits `0x10`, `0x20` and `0x80`) and the informational flag `containsUnmappedGlyphs`. Omitting either spare value, or sending null, retains its stored value. Explicit zero clears it. Mode values 0 through 5 occupy the low nibble; blank-before is bit `0x40`. Reserved masks containing assigned bits are rejected.

An authored message accepts up to 20 NFC-normalized display cells from printable ASCII and the supported Western terminal glyph set. The encoder uses the terminal character codes, not UTF-8 or ISO-8859-1 byte values; for example, the character é encodes as `0xA6`. Unknown imported cells are shown with a replacement glyph or a blank for embedded zero. When the text is unchanged, the underlying bytes remain intact even if other fields are edited. To replace such a message, send supported text in the entire field. The API does not infer or write a separate language selection from the content.

The schedule request takes the same selection plus `availableAtUtc`, either an ISO 8601 date and time with its offset or null for immediate availability. Each phone can have one open scheduled download. A call-in can pick up the set once it is available. Failed attempts remain ready for the next call. The existing assignment stays effective until the terminal acknowledges the scheduled download. An operator assignment made during delivery takes precedence.

Field updates include the `revision`, `sha256`, `profile` and a `changes` object keyed by field ID. The API rejects stale revisions and leaves bytes outside the changed fields intact. For matching layouts with the same size, pass `profile` in the read query.

The field schema includes `isSpare` for a typed reserved control and `displayGlyphs` for a text field using the verified Western terminal character mapping. Both are informational schema properties; edit the corresponding field by its key in `changes`. Spare flags accept the same `"true"` or `"false"` values as ordinary flags; spare bytes accept decimal strings from 0 to 255 and unsigned little-endian spare words accept decimal strings from 0 to 65535. Only fields defined for the selected profile are accepted. Unmapped display text has a null read value and is preserved when omitted.

MT50 offers a 105-byte inactive template, shared by the older and both later profiles. It begins with all coin windows and acceptance flags disabled and zero values, volumes and capacities. The coin settings must be calibrated for the target validator before use.

Graphical screen-type changes replace the 1044-byte body union and initialize new mixed-panel links when applicable. The two outer control spare bytes and main key bytes are unaffected. Bitmap and text spare IDs differ so an old body-specific edit cannot silently write to a new screen type. The packed icon alias remains available to older API clients; the console uses the masked field and independent spare flags.

Slots in field keys are zero-based. Explicit spare edits preserve unrelated fields. Blank, Delete and Clear retain the identified spare values; changes to a selected slot cannot be combined with an incompatible staged blank/delete/clear operation in the same save.

The card sequence GET returns `available`, `editable`, a one-based `slots` list with `blank` and `movable` flags, `carrierNumber`, and `cards` and `carriers` stamps containing `revision` and `sha256`. For POST, send distinct one-based `from` and `to` positions and both observed stamps. The destination must be blank. A matching complete carrier record is required. The response contains the updated stamps and `carrierChanged`; when no bitmap bits change, the carrier keeps its original revision. HTTP 409 indicates that either record is stale or missing, or the set has been published. Invalid positions or layouts return HTTP 400. Get requires Table records Read; move requires Table records Update. This is a draft edit, not a queued download.

The same card sequence GET includes unambiguous `carrierReferences` and, for each configured position, its `master` identity and applied revision (if linked), recognized target `mapping`, and `acceptedCarriers`. Add takes both record stamps, `definitionId`, `definitionRevision`, the complete destination `mapping` keyed by native field ID, and `acceptedCarriers` (an explicit list, which may be empty). The first recognized blank position is selected atomically. Link takes both stamps, the definition identity/revision and `position`; it rejects a wire-byte mismatch. Refresh takes the linked `position`, the latest `definitionRevision` and both stamps. Omit both `mapping` and `acceptedCarriers` to preserve the current target references and carrier bytes, or supply both to explicitly remap. Remove takes `position`, both stamps and `confirm: true`. The response reports the affected position, updated stamps and whether carrier bytes changed. These mutations require Table records Update; add, link and refresh also require Card master list Read.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/card-master?tableNumber=22&includeArchived=false` | List reusable definitions, optionally filtered by MT22 or MT134 |
| GET | `/api/card-master/schema?tableNumber=22&standard=1` | Read the typed template sections for a profile and card standard |
| GET | `/api/card-master/{id}` | Read a named definition and its native sections |
| POST | `/api/card-master` | Create a named definition from typed changes or a saved card row |
| PUT | `/api/card-master/{id}` | Update a definition using its observed `revision` |
| DELETE | `/api/card-master/{id}?revision=1&confirm=true` | Archive a definition without modifying existing snapshots |
| POST | `/api/card-master/{id}/restore?revision=2` | Restore an archived definition |
| GET | `/api/card-master/{id}/usage` | List linked sets, positions, applied revisions and assigned-phone counts |

Master definition input is `code` (up to four characters), `name`, `tableNumber`, and `changes`. Create may additionally include `source: { setId, position, revision, sha256 }` to copy a complete configured row using its observed record stamp. Fields are profile-specific and use the ordinary native field IDs. Master definitions retain their own revision. Editing them does not mutate linked records. The stored link tracks the exact applied row hash and definition revision. An unrelated direct edit preserves the link; a modified linked row detaches. Row movements, clones and record copies retain applicable links. Usage additionally requires read access to Table sets, Table records and Table assignments.

The master schema and detail responses identify typed reserves with `isSpare`. Master application and refresh copy the complete row, including its reserves, while preserving reviewed destination-specific mappings. A reserve-only change uses the same revision and membership rules as any other row change.

Rollout preview takes `revision`. It returns a `previewToken`, grouped configuration positions, `eligiblePhones`, `scheduledPhones`, `metadataOnlyPhones`, and `skippedPhones`. Apply takes the same revision and the exact token. It recomputes the result in a serializable transaction, creates new published snapshots, updates desired assignments with rollback history, and stages selected batches only for changed card bytes plus declared dependencies. Stale state returns HTTP 409. Apply requires Card master list Update and the existing Table set Add/Update, Table records Update, Table assignment Update and Downloads Add permissions in addition to usage read access.

MT55 offers a 571-byte template for each editor profile. Field IDs use zero-based `key-{row}` prefixes. `customerReference` is a four-byte unsigned value and the `rate` byte carries the tariff index or carrier reference according to the key flags. To clear keys, include `clearQuickAccessKeys` with distinct one-based slots from 1 through 10. Save edits to other slots in the same request. The API rejects an edit and a clear for the same slot.

MT58 offers separate 26-byte templates for the older and later profiles. `restriction` accepts values 0 through 3 on the older profile, and 0 through 4 on the later profile. `startHour` and `startMinute` use phone-local time; `durationHours` and `durationMinutes` define a positive daily window up to 24 hours. The firmware caps the maximum interval at 86,399 seconds. No-change saves preserve all imported bytes, including the 20 reserved bytes. Changed active configurations must have a supported level and valid time values. Publication checks imported active records against the target. Later level 4 additionally reports an advisory if no included MT55 or MT92 route is marked for configurable restricted access, distinguishing omitted companion records from present but unconfigured ones.

MT68 is a conditional 72-byte Audio-Gram configuration record for a compatible switch service. `statistics` retains its `0` or `1` API values while editing only bit 0 of byte 21. `lineReleaseDelay` is the seventh timing word at offsets 56 and 57, labeled Voice Prompt Play Delay in the legacy manager. `spare4` and `spare5` are words at offsets 58 and 60; `spare6` through `spare15` are bytes at offsets 62 through 71. The separate `statisticsSpare`, `callSpare` and `paymentSpare` fields edit only the named flag bit. The service key is write-only. Firmware review checks enabled access settings and reports that the matching length does not prove service support. Provisioning review also reports missing permitted call/payment types and timing or signaling conflicts.

MT32 and MT34 have inactive draft templates. MT34's `enabled` field now edits the optional CDR mode bits only (mask `0x1D` at offset 13), with values `0`, `1`, `4`, `8` and `16` for normal, all attempts, completed, completed except local coin, and completed except local coin/stored-value. `carrierStatistics` separately edits bit 1 in the older profile and bits 1 and 5 in the later profile. The field values are `0` for off, `1` for per carrier, and `17` for later combined reporting (encoded as `0x22`); the reserved bits survive unchanged. Imported noncanonical combinations remain visible and byte-identical on a no-change save. Active schedule review distinguishes malformed time values from advisory timestamp and collection dependencies. The `detailThreshold` is an optional-window threshold; MT35 supplies the normal threshold. MT32 exposes its existing timing bins plus the typed reserved timing pair at offsets 9 through 12.

MT32's `interval-{index}.start` and `interval-{index}.duration` fields use nonnegative signed 16-bit little-endian values in 10 ms ticks, at offsets `1 + 4 * index` and `3 + 4 * index`, for indices 0, 1, 3 and 4. Index 2 is the separate reserved timing pair. The seven MT37 histogram ranges have boundaries `start`, then `start + 1*duration` through `start + 5*duration`; comparisons are strict upper bounds, and the last bucket is the remainder. The inspected terminal uses a 16-bit unsigned accumulator for these boundaries. For an active collection policy, firmware review adds nonblocking findings for negative imported values or a final boundary above 65535 ticks. The browser previews only normal representable ranges from the selected record and never labels historical MT37 reports using current MT32 values. No new endpoint or field encoding is required.

MT24, MT59 and MT92 field responses include `screening.descriptions` and `screening.supportsSpeedDial`. Send `screening.descriptions` as an object keyed by one-based slot, with descriptions up to 120 characters or an empty string to remove one. These text edits change the record revision and preserve the wire SHA-256. Draft copies and record copies carry descriptions. A raw record replacement resets the descriptions because slot contents may have changed.

For an unconfirmed 1,021-byte MT59, the field endpoint returns the possible layout names in `profiles`. Pass the confirmed name as the GET `profile` query parameter and the PUT `profile` field. The first changed save or initialization from a template records the selection. Subsequent conflicting layout requests are rejected. Draft copies and record copies carry the selection, and raw replacement resets it.

Send `screening.actions` with distinct `slot` and `action` values. `blank` clears the pattern and description, plus the trailing wildcard count on expanded layouts. `delete` also resets supported slot settings. The slot remains in its original position. The later 180-slot MT92 accepts `speedDial` with `shortcut` and a full numeric `destination` that fits the 16-digit pattern. A star shortcut writes the packed alias. An N11 shortcut also sets the translation flag. For ordinary pattern fields, `?` writes the single-digit wildcard nibble.

For the 353-byte MT62 numbering plan, the field response includes `numberingPlan.dial` and `numberingPlan.format`. A null value means the corresponding layout could not be decoded. A field update can include a `numberingPlan` with either or both complete rule arrays. Each row contains `id`, `noMatch`, `match`, `control`, `tag`, `callType` and `digits`. Dialing rows can also include `conversion` or `maximumDigits` when enabled by the control byte. Link values are row IDs, with null indicating an absent link. The first row is the entry point. The API repacks links, validates the match and fallback paths, and rejects edits that exceed capacity or overwrite unrecognized bytes. Use `changes` in the same request to edit currency or other numbering-plan settings. The MT62 `keyCardNumber` field is write-only.

The field response also includes `numberingFormatCapacity`: 132 for the older profile or 140 for the verified later standard and graphical Multi-pay profiles. Both dialing regions are 180 bytes. The older currency fields occupy 345..352; those bytes belong to display-formatting rules in the later profiles and cannot be edited as currency. The profile-aware decoder, writer and publication review use the same region sizes. A fixed-size formatting edit includes its terminating byte when preserving imported rule offsets. An unchanged empty rule set round-trips; removing the last active dialing rule remains invalid.

MT26, MT31 and MT62 keep the older layout as the default when a set has no verified firmware target. The `profiles` array lists the applicable choices. Use the selected `profile` in the update. The MT31 `craftAccessCode` and `keyCardNumber` fields are write-only. Omit either key from `changes` to keep its stored value.

The MT26 reroute switches are ordinary boolean fields independent of card validation and carrier acceptance. Provisioning findings continue to report incompatible carrier acceptance even when alternate routing is permitted, since that switch alone does not establish a working alternate carrier.

MT22, MT23, MT134 and MT135 have inactive templates. In the field response, `card-{row}.format` selects the standard and the editor exposes the corresponding data sections. A save can select a standard and set its new fields in the same request. Moving between card families clears the shared 20-byte area for the row. Supply three digits for a service code or an empty string to end the list. The API rejects gaps and active data-spill steps after an end marker. MT23 and MT135 accept carrier control fields, with terminal-rate permissions available on MT135. Enabling Feature Group B requires a positive screening entry reference. Set detail includes nonblocking `provisioning.findings` for carrier references, conflicting duplicate identifiers, defaults and payment permissions in supported record pairs. Free Feature Group B entries in MT55 and MT92 use a carrier identifier instead of a tariff index. For the documented Multi-pay targets, `firmwareFindings` reports unresolved identifiers or dependence on the installed MT23 or MT135 without blocking a partial download.

The reusable carrier library is available at `GET /api/carrier-library?tableNumber=23` (or 135), with a typed template at `GET /api/carrier-library/schema?tableNumber=23`. Create with `POST /api/carrier-library`, supplying `code`, `description`, `tableNumber`, and `changes` using the `carrier-0.*` field keys. Optionally supply `source: { setId, slot, revision, sha256 }` to import a saved row. Slot indexes are zero-based. Read/update/delete a definition at `/api/carrier-library/{id}`; updates and deletes require the observed library revision, and deletion requires `confirm=true`. To apply to a draft, post to `/api/carrier-library/{id}/apply` with `setId`, `slot`, `libraryRevision`, `recordRevision`, `recordSha256`, `keepCardAcceptance`, and an explicit `screeningEntry` when Feature Group B is active. The optional `copySpareFields` boolean defaults to false, preserving the destination row's reserved fields. True copies just the definition's typed reserved row fields. The card acceptance choice remains independent, and the tail of the full record is not copied. Library schemas and details identify spare controls with `isSpare`. This creates a new record revision only if its bytes changed. Library Read plus Table Records Update are required for apply; importing a source row requires Library Add plus Table Records Read. No library operation mutates a published table snapshot.

MT93 has two 225-byte profiles. A set with a verified firmware target uses that target's layout. Otherwise, pass the selected `profile` when opening or updating the record. The `validation-key-{index}` fields use `editor: "password-hex"` and always return a null value. To replace a slot, send exactly 16 hexadecimal characters from the firmware-formatted key material. Omit the field or send an empty string to preserve it. On the later profile, each `discount-{row}.{zone}Mode` accepts `0` for a signed adjustment, `1` for a percentage of the normal charge, `2` for a replacement tariff, and `3` for disabled. Changing the method resets that call zone's two stored values. The same request can set the new `{zone}Initial` and `{zone}Later` values.

The visual prompt records MT27/28 have 140 fixed 20-cell rows, and MT85/86/98/99 have 400. The native field key is `prompt-{zeroBasedRow}.text`, with a fixed record offset of `1 + 20 * row`. The worksheet uses the existing revision and digest checked field update, not a new endpoint. It submits only staged field keys. A decoded no-op preserves the original bytes; an omitted field retains its bytes, including unmapped glyphs; an explicit empty string clears a selected row. The client export document format is `coinline-visual-prompts-v1` with `recordNumber`, `rowCount`, and a `rows` array of objects containing `row` and `text`, plus an informational label. In import documents, null and absent rows mean retain, not clear. Only the verified matching fixed-layout records are accepted by the worksheet.

The 1,001-byte MT72 profile has a blank template and named settings for the assigned portion of its payload. The `spareBytes` property contains 2,000 characters, with one hexadecimal pair per payload byte and `??` for each protected byte. The first pair is wire offset `1`. The message type at offset `0` is fixed. In a draft update, send `spareBytes` as an array of `{offset, value}` objects with integer offsets `1` through `1000` and integer byte values `0` through `255`. A write rejects duplicate offsets, protected bytes and bytes that are also part of a named field in `changes`. Use the write-only native fields to replace protected data. The `operatorPin` field also accepts `clear` to remove the stored PIN. Both kinds of edit use the same revision and digest checks.

The 21-byte MT35 template starts with a daily 02:00 call-in, a five-minute retry delay and a call-record threshold of 30. Use `startTime` with `HH:mm:ss` or `HH:mm` to edit the time of day. Use `adjustAt` with `YYYY-MM-DDTHH:mm:ss` or `YYYY-MM-DDTHH:mm` to set a one-time update of the terminal clock by the signed `adjustment` seconds. Send an empty `adjustAt` to disable the update. The individual byte fields remain available for imported records. Send either a formatted time or edits to its component bytes in a request.

The later 263-byte MT49 profile has a draft template. The `delay` and `wink` timing values use 10 ms units. The record has 16 patterns with up to 20 keypad digits each. Each pattern has a numbering-plan reference and an encoded supervision definition byte. Updates preserve reserved bytes. The existing 199-byte layout remains available for imports.

The 1,192-byte MT73 template starts with 128 unavailable tariff rows. The `initialPeriod` and `additionalPeriod` fields use signed seconds with `-1` for unlimited. The editor also accepts the previous unsigned value `65535` for that sentinel. New finite periods accept `0` through `32767` seconds. Charge fields remain unsigned cents.

MT150 and MT151 offer templates and return a `tariffIndexOffset` on rate references. The API uses wire codes `0` for host rating and `1` for rejection. For MT150, codes `2` through `15` add 14 to get the MT73 row. For the inspected MT151 layout, codes `2` through `99` add 28. The MT151 `noMatch` field selects host rating (`0`), its configured `fallback` code (`1`), or rejection (`2` or `3`). A zero country or destination prefix leaves the slot unused.

Local-dialing templates are available for the 819-byte uncompressed, 403-byte compressed and 203-byte double-compressed records. `areaCode` accepts a three-digit value from `200` through `999` and writes the firmware's packed comparison value. Send an empty string or `000` to disable the segment. Exchange fields write direct MT73 row numbers within the selected format's capacity. An edit preserves the other exchanges and the reserved header bytes.

MT152 stores two periods per day group in weekday, Saturday, Sunday and holiday order. End hour `24` requires end minute `0`. Holiday rows accept a real month and day or two zeros. For each zone, send `period-{row}.{zone}Index` with the zero-based MT93 discount slot `0` through `9`. Send `period-{row}.{zone}Payment` with `0` for disabled, `1` for coins, `2` for cards or `3` for both. The zone keys are `local`, `intra`, `inter` and `international`. The original `period-{row}.{zone}` fields still read and write the whole packed byte. Use either the packed field or its component fields in a save.

The 100-byte MT94 profile has an inactive template. Use `startAt` for the UTC time on the terminal clock, without a timezone suffix. The API also accepts the individual `start.*` fields. `start.year` counts from 1900. Use one date input method per edit. `modemSpeed` accepts `1` for 1200 baud and `2` for 2400 baud. The existing `sector-{index}` field keys select 4 KiB code blocks `0` through `255`. To replace `serverAuthentication`, supply exactly 12 hexadecimal characters. The field returns a null value.

Use `targetType=region` with `regionCode` and omit `targetId`. Use `targetType=group` with the group GUID as `targetId` and an optional `regionCode` for the intersection. The matching region codes come from `GET /api/terminals/regions`. This scope applies to assignment preview, full assignment, record update and scheduling. Region codes match case-insensitively.

Use `targetType=group-pattern` with `groupPattern` and an optional `regionCode`. Omit `targetId`. The pattern starts with three literal letters or digits and has at most six characters. Use `?` to match a single position and a final `*` to match the remaining suffix. Matching uses the stored group IDs case-insensitively and includes primary and additional group memberships.

Use `targetType=time-area` with `timeAreaCode` and omit `targetId` for a schedule preview or confirmation. Eligible deliveries are MT35 call-in parameters alone or a dedicated MT94 firmware set. For a source containing multiple records, select MT35 explicitly. A successful MT35 schedule delivers that record as a partial download. `GET /api/terminals/time-areas` lists the codes currently in use.

For a partial data schedule, pass repeated `recordNumbers` query parameters in the preview and a `recordNumbers` array in the schedule request. The preview returns the full selection including dependencies and tests the eligibility of the records that will be sent. Confirm the eligible terminal IDs from the preview. The schedule history returns the same resolved record numbers in transmission order. A completed partial schedule leaves the normal full-set assignment in place. Omitting the selection schedules the full set.

`availableAtUtc` is the earliest time the host can prepare a scheduled batch. Omit it to prepare the batch during the scheduling request. History reports actual `preparedAtUtc`, the latest pickup `startedAtUtc`, completion and `lastBatchId`. A prepared batch is `Ready` before the phone contacts the host. Pickup attaches to that batch, and a failed attempt remains in download history when the next eligible call starts a retry. Cancel using the schedule endpoint to cancel any prepared items as well.

To name a draft record, send its current `recordRevision` and `configurationId` to the record Configuration ID endpoint. Send `null` to clear the ID. IDs allow up to six printable ASCII characters with no leading space. CoinLine discards trailing padding and stores uppercase. The ID is host metadata. It survives payload edits, draft copies and record copies, and leaves the wire hash intact.

Use `targetType=configuration-id` with `configurationId` and a single explicit message type in `recordNumbers` to schedule a named configuration. The published source record must carry that ID. Eligible candidates have the same ID on the same message type in their current published assignments, including assignments from other sets. The preview resolves any required records and applies the usual customer, firmware and terminal checks. Confirm the eligible terminal IDs from the preview. CoinLine rechecks the candidates before scheduling.

Use `POST /api/tables/sets/{id}/schedules` for a published set containing only MT94. `availableAtUtc` determines when a call-in can pick up the record. When enabled, `startAt` must be later than `availableAtUtc`, or later than the current time for immediate availability. If a phone first calls after the enabled terminal start time has passed, the host cancels the pending delivery. A disabled record can be scheduled to clear the terminal’s code download schedule. A successful MT94-only delivery belongs to the firmware schedule history and is independent of the phone’s regular table assignment.

The schedule list includes `canQueueFirmwareCancellation` for the latest delivered, enabled MT94 when the phone has no open scheduled delivery. Use `POST /api/tables/sets/{id}/schedules/{scheduleId}/clear-firmware` to prepare that cancellation. The response contains `scheduleId`, `tableSetId` and `batchId` for a new immediate schedule. Its published record preserves the delivered parameter bytes except for the enable bit. The original delivery remains in history. A stale or conflicting request returns HTTP 409. The cancellation batch requires its own terminal acknowledgement.

For an MT94-only set, use `targetType=terminal-id-range` with `firmwareTarget.terminalIdFrom` and `firmwareTarget.terminalIdTo` in the preview query. Both are inclusive ten-digit decimal wire IDs supplied as strings. Use the same ID in both fields for one phone. Use `targetType=software-version` with `firmwareTarget.currentControlRom` and `firmwareTarget.currentControlSoftware` to match the latest complete terminal-originated NCC MT60 report. The two labels are case-sensitive after trimming padding and are limited to seven and four printable ASCII characters respectively. Omit `targetId` for either scope. Send the same fields inside the `firmwareTarget` object in the JSON schedule request, with the eligible `terminalIds` from the preview.

The firmware preview keeps existing pending or delivered firmware schedules by default. Pass `allowFirmwareReschedule=true` in the preview query and in the subsequent JSON request to replace them. For each eligible phone with an existing firmware schedule, the preview returns `replacesFirmwareScheduleId`. Pass those exact IDs in `replacesFirmwareScheduleIds` along with the eligible phone IDs. The confirmation rechecks both sets and returns HTTP 409 if either changed. A pending data download or active firmware transfer excludes the phone. A successful confirmation cancels replaced pending batches and preserves previously delivered records. The response includes `scheduled`, `replaced` and `skipped` counts.

To allocate starts across a repeating daily firmware download window, add `firmwareWindow.startDate` (UTC date), `firmwareWindow.dailyStart` and `firmwareWindow.dailyEnd` (HH:mm), `firmwareWindow.activeServers` (1 to 99) and `firmwareWindow.slotMinutes` (estimated total minutes per phone) to the preview query. The preview returns a `firmwareAllocation` summary with the raw transfer lower bound, first start, last slot end and `previewToken`. Each eligible target includes `firmwareStartAtUtc`, `firmwareSlotEndAtUtc` and `firmwareServerSlot`. Confirm using the same inputs in the JSON `firmwareWindow` object (serialize times as HH:mm:ss), the exact eligible IDs and `firmwarePreviewToken`. Parameter availability must precede the first allocated start. Each distinct start produces an immutable published record with only the six calendar bytes changed. Schedule history returns the actual `tableSetId` and original `sourceTableSetId`; pending cancellation or delivered firmware clearing can be requested through either ID. The `firmwareSlotEndAtUtc` is a host planning estimate. Terminal MT94 contains the start time only.

The `firmwareAllocation.existingReservations` count identifies future window reservations considered for the same encoded code-server route, across source sets and jobs. Allocation checks peak simultaneous reservations over each complete slot. `fixedTimeSchedules` counts enabled fixed-time parameters starting on or after the first window that lack a duration. Replacement of an undelivered schedule releases its reservation atomically. For delivered parameters, CoinLine retains the reservation until the slot ends or the phone acknowledges a newer firmware record. Window confirmation uses a serializable transaction and rechecks the preview token. A capacity change requiring a new preview returns HTTP 409.

Visual prompt sections with `showDisplayPreview` set contain the upper and lower fields of a known two-line message in display order. Each `prompt-{row}.text` key still addresses one zero-based, 20-byte wire row. Supported Western accents are converted to the firmware's glyph codes. An unmapped imported row returns a null value and is preserved when omitted from `changes`.

Graphical records MT131 through MT133 expose fields based on the screen type. A field ending in `.kind` accepts `0` for undefined, `66` for bitmap, `77` for mixed, or `84` for text. The API can apply a type change and the new content in the same request. A type change reinitializes that screen's content area. Text uses newline-separated rows. A screen link packs the zero-based screen index into the low six bits and the panel into the high two bits. Value `255` means no link.

Graphical screen and mixed-panel `.dwell` values use 10 ms ticks. The two nibbles in `.flash` and the MT131 `offHookDuration` field use seconds.

`POST /api/tables/sets/{id}/graphical-starter` takes `enableSampleMenu` (boolean, default false). It adds MT131, MT132 and MT133 to a draft using the supplied default artwork, with an optional off-hook menu that navigates locally. The response includes the number of records created and their message types. An existing matching record is retained, making an exact retry idempotent. A conflicting existing record returns HTTP 409 without replacing any records. A known incompatible target profile returns HTTP 400. The endpoint requires Table records Add permission and does not publish or assign the set.

The MT68 `serviceKey` field is write-only in the native field API. Omit it from `changes` to keep the stored key. The field response provides `editor: "password"` and `value: null`. Enabling messaging requires a valid service number and key.

## Quick Access Key Customer Directory

| Method | Path | Operation |
| --- | --- | --- |
| POST | `/api/quick-access-customers/search` | Search directory summaries, including archived entries if requested |
| POST | `/api/quick-access-customers/lookup` | Search active references and names for an MT55 key |
| GET | `/api/quick-access-customers/{id}` | Read one directory entry, including its contact and billing notes |
| POST | `/api/quick-access-customers` | Create an entry with a unique six-digit reference |
| PUT | `/api/quick-access-customers/{id}` | Update details using the current revision |
| DELETE | `/api/quick-access-customers/{id}?revision={revision}&confirm=true` | Archive an entry without reassigning its reference |
| POST | `/api/quick-access-customers/{id}/restore?revision={revision}` | Restore an archived entry |

Search and lookup accept a JSON body with `query`, `page` (one-based), and `sort` (`reference` or `name`). Search also accepts `includeArchived`. Each returns `rows`, `total`, `page` and `pageSize`. Lookup returns only `reference` and `name` in each row and always excludes archived entries. Search returns those fields plus `id`, `revision` and `archived`. Search terms belong in the body rather than the URL.

Create and update use `reference` (a six-digit string, not `000000`), `name`, and optional `billingComments`, `contactName` (up to 40 characters), `phone`, `street`, `city`, `province`, `postalCode`, and `notes`. Update replaces those details using `revision`, including empty values to clear optional fields. References cannot be changed or reused after archiving. Duplicate references and stale revisions return HTTP 409. Administrative directory responses are not cached; directory audit details omit contact and billing contents.

Search and full details require Quick Access Key customer directory Read. Creation, revision updates or restoration, and archiving require its Add, Update and Delete rights respectively. A separate Quick Access Key customer reference lookup Read right can use the minimal lookup endpoint without the full directory permission. The two permissions do not grant Table records Update.

Selecting a reference stages the existing MT55 native field `key-{zeroBasedSlot}.customerReference` as a decimal string; existing `fields` revision/hash protection and Table records Update apply. Both 571-byte profiles store a four-byte unsigned little-endian value at offset `1 + slot * 57 + 51`; zero is blank. Imported non-directory values remain valid for byte-preserving editing. Directory contact information is never included in that wire field or any generated download.

**UI:** `/quick-access-customers` and the per-key lookup on `/table-sets/:id`.

## Inmate Feature Configurations

| Method | Path | Operation |
| --- | --- | --- |
| GET | `/api/inmate-features/schema` | Read editor sections, field IDs, defaults, choices and limits |
| GET | `/api/inmate-features` | List saved configurations |
| POST | `/api/inmate-features` | Create a named configuration |
| GET | `/api/inmate-features/{id}` | Read settings and the current revision |
| PUT | `/api/inmate-features/{id}` | Update a configuration using the current revision |
| DELETE | `/api/inmate-features/{id}?confirm=true&revision={revision}` | Delete the selected revision |

Create and update take `name`, `description` and `settings`. The field schema supplies the defaults used on creation. Omitted settings retain their values on update. Field errors include the settings key. A stale revision, duplicate name or deletion of an assigned configuration returns HTTP 409. These configurations are saved separately from table sets until an Inmate terminal wire layout is verified.

| Method | Path | Behavior |
|---|---|---|
| GET | `/api/terminals/{id}/inmate-configuration` | Read the named references, available feature choices, family eligibility and current revision |
| PUT | `/api/terminals/{id}/inmate-configuration` | Save the feature configuration ID and external setup Configuration ID using the observed revision |

The PUT body requires `featureConfigurationId`, `setupConfigurationId` and `revision`, which may be null. An initial assignment uses a null revision; subsequent writes use the returned revision. Setup Configuration IDs use the existing six-character configuration identifier format. Non-Inmate phones cannot receive new references but can clear retained assignments. The response identifies that the wire format is unverified. No download batch, scheduled record or table-set assignment is created by these endpoints.

**UI:** `/table-sets`, `/table-sets/:id`
